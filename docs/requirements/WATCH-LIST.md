## Added in Lecture 15

| Requirement | Watch for | Status as of Lecture 15 |
|---|---|---|
| POST /api/posts and authorId (Lectures 7 to 9, 14). | Watch for any route that reads an identity field out of the request body. | **Closed.** requireAuth verifies the bearer token and the route uses req.user.id. A request with no token is a 401, and a request carrying somebody else's id in the body saves the post under the token's owner instead. Both are covered by tests, so a future change that reopens this fails the suite. |
| A valid token for a user who no longer exists (the rest of D-005). | Watch for a 500 on publish after an account is deleted. | Open. I deleted a user, kept their unexpired token and published: still a 500 from Prisma's foreign-key error. requireAuth proves the token was signed by this server, not that the account is still there. The fix is to look the user up (or check a token version) and return 401, which also gives a way to revoke a token before it expires. |
| Rate limiting is keyed by IP address. | Watch for several people on one network locking each other out, and for an attacker who simply spreads attempts across addresses. | Open, and a genuine trade-off rather than an oversight. Keying by account instead would let an attacker lock a victim out of their own account by failing on purpose. The real answer is both keys at once, which is more than this lecture needs. |
| Nothing limits successful account creation. | Watch for a script that registers thousands of real accounts. | Open. skipSuccessfulRequests means the register limiter counts only failures, so bulk sign-ups pass straight through. A second, slower limit on all register requests would cover it, but it has to stay loose enough not to break the test suite, which registers a user per test. |
| Stored XSS in post bodies. | Watch for dangerouslySetInnerHTML, or a Markdown or rich-text renderer being added to PostCard or Feed. | Guarded, not fixed, because there was nothing to fix: React escapes text already. PostCard.security.test.jsx fails if that changes — confirmed by switching PostCard to dangerouslySetInnerHTML and watching the test fail. One caveat worth writing down: jsdom does not execute a script inserted through innerHTML, so the `window.__xss` assertion in that test passes even in the vulnerable version. The assertion that actually catches the regression is the one looking for the script tag as literal text. |
| The rate limiter's counter is in memory. | Watch for a lockout that disappears after a deploy, and for the day Inkwell runs more than one server process. | Open, and the same shape as the Lecture 9 stats counter. Restarting the server clears every lockout, which I hit for real: the Playwright suite failed at its login step until I restarted the server, because the figure I captured for the report had used up the budget for 127.0.0.1. With two server processes an attacker would get five attempts per process. A shared store (Redis, or the database) is the usual answer. |
| The feed now returns each post's author, but no page shows it. | Watch that a byline added to PostCard reads post.author.displayName and not some wider user object. | Open, cosmetic. Section 1.4 shapes the author onto every feed and search result; PostCard still renders only the title and body, so the data is there and unused for now. |
